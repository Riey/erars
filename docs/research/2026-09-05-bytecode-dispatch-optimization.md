# Bytecode Interpreter Dispatch Optimization (`bytecode-opt` branch)

Date: 2026-09-05
Scope: `crates/erars-vm/src/terminal_vm.rs`, `crates/erars-vm/src/terminal_vm/executor.rs`, `crates/erars-vm/src/function.rs`, `crates/erars-vm/src/context.rs` (`VariableStorage::index_local_var`/`index_var`), `crates/erars-vm/src/variable.rs`, `crates/erars-vm/src/inst_counter.rs`, `crates/erars-compiler/src/{compiler,instruction,parser}.rs`, `crates/erars-bytecode/src/lib.rs`, `crates/erars-lint/src/lib.rs`, `crates/erars-stdio/src/{main,stdio_frontend}.rs`. Branch `bytecode-opt`, based on `master` at `35435b9`, six commits: `42840c7` (census tool), `b006989` (A/B harness), `e4723cf` (P0: dispatch match), `99c95fb` (P0 follow-up: `index_local_var` fix), `d0f1162` (P1v2: `ReportPosition` elimination), `1d5a8df` (`index_var`'s global-path fix, §9), `88cb4cc` (real-workload replay harness + dynamic instruction histogram, §11).
Method: real corpus census (`jit_census` example) against two production ERB corpora (`eraTHYMKR`, `eramegaten_p_kr/Data`) to find where dispatch cost concentrates; a real-`TerminalVm`-execution A/B microbenchmark (`jit_ceiling_bench` example) to measure whether a candidate change actually helps, with a dynamic-instruction-histogram correctness guard on every change so a speed measurement can never be trusted without first confirming it didn't also change *which* instructions run.

**Caveat that applies to every timing number in this document except the corpus load-time, static-instruction-count, and real-workload sections**: `jit_ceiling_bench`'s interpreter-loop timings come from one synthetic ERB loop (`LOCAL`/`SUM`/`PRINTFORM`, statement mix tuned to approximate the census's corpus-observed unigram proportions — see §1 and §2) executed 3,000,000 times. This approximates, but does not equal, either real corpus's actual instruction mix or control-flow shape. An earlier draft of this document claimed running a real corpus's actual game loop end-to-end "is not automatable here — it is an interactive text game"; that claim was false and unchecked (see §12's methodology note) — `erars-stdio --use-input <ron-file> --exit-when-input-exhausted` drives a real corpus fully headlessly, with no interactive terminal required (`< /dev/null` and all), and §11 does exactly that against eraTHYMKR. §7's corpus numbers are a load-time/size/static-count cross-check; §11 is the actual corpus-driven runtime-execution cross-check this document previously claimed did not exist.

## Summary

**What changed and what it costs.** Three stages (P0 dispatch-match, §3; `index_local_var`'s TARGET-read fix, §4/§6; `ReportPosition` elimination, §6; plus `index_var`'s matching global-path fix, §9) together cut the synthetic `jit_ceiling_bench` loop's dispatch time by a measured **-21.25% median** (§8) — but that number has a real, non-free counterpart, and burying it in a validation section (as an earlier draft of this document did) understates it:

- **Load time: +0.92% (eraTHYMKR, weak/noisy signal, 8/10 round sign agreement) to +2.31% (eramegaten, 10/10)** (§7).
- **Net +3 bytes per compiled statement, verified by byte-level reconciliation, not estimated**: the old `ReportPosition` instruction was 5 bytes; its replacement is an 8-byte `(u32, u32)` positions-table entry plus a 4-byte per-function length prefix the old format never had. Predicted vs. measured `game.era` growth agree to within the corpus's own ~100-300 byte run-to-run noise floor (eraTHYMKR: 2,506,181 B predicted vs. 2,506,243 B measured median, 62 B gap; eramegaten: 3,190,400 B predicted vs. 3,190,310 B measured median, 90 B gap — see §7). A verified-viable (not speculative) mitigation exists if this cost ever needs cutting: both corpora's line numbers fit comfortably in a `u16` (max observed 35,398 and 11,107, both well under 65,536), which would shrink the entry to 6 bytes and the net delta to roughly +1 byte/statement instead of +3.
- **The synthetic -21.25% does not directly predict real play.** A real, played eraTHYMKR session (§11) shows a smaller, still-real, still-10/10-sign-agreeing improvement: **-9.45% median in game-loop-only time** (isolating post-load dispatch cost, 7.73-11.83% range) and **-3.15% median in full-session time** (load included). The gap exists because a real session's dynamic instruction mix is broader than the synthetic loop's `LOCAL`/`SUM`-heavy profile, and — the arc's central methodological point — because *static* instruction-occurrence counts (what §1's census measures) and *dynamic* execution-frequency (what actually happens when the code runs) are not the same measurement and do not even agree on which instructions dominate (§11).
- **P2: fusing `LoadStr`→`LoadVarRef` into one instruction — arc-wide `game.era` size now net *below* the pre-arc baseline (§14).** A census found `LoadVarRef` (§1's third-largest static category) is preceded by a dedicated `LoadStr` push of its own variable name in **100.0000%** of ~1.4M combined occurrences across both corpora, never anything else — the same one-producer-one-consumer redundancy pattern §1/§6 already exploited for `ReportPosition`. Fixed by folding the observed `count` range (0-3 across both corpora) into 4 new `InstructionType` discriminants (`LoadVarRefNamed0..3`) rather than packing it into the already-full 4-byte instruction payload, eliminating one dispatch and 5 bytes per occurrence with zero truncation risk; `count > 3` (unobserved in either corpus, but real reachable code) falls back to the classic two-instruction form unchanged. Real THYMKR replay: **-8.58% median game-loop-only time**, 10/10 sign agreement. `game.era` shrinks **-6.24% (eraTHYMKR) / -4.76% (eramegaten)** of the pre-fusion size — enough to overshoot §12's own mitigation and put the arc's cumulative size change at **-4.65% (eraTHYMKR) / -2.95% (eramegaten) relative to the pre-arc `35435b9` baseline**, net negative for the first time in this arc.

**Every timing claim in this document follows §12's measurement protocol** (build variants first, interleave both orders, ≥10 rounds, report per-round deltas and explicit sign agreement, `uptime` before/after). See §12 also for a methodology note on two now-corrected unchecked negative claims this arc made along the way.

## 1. Where dispatch cost concentrates: the unigram/bigram census (`42840c7`)

`crates/erars-loader/examples/jit_census.rs`, adapted from the `llvm-jit` branch's AOT-feasibility spike (`d5c9d68`), loads a real corpus's compiled `FunctionDic` and counts every instruction's static frequency (unigram) and every adjacent same-function-body instruction pair (bigram; pairs never cross a function boundary). Re-run against both corpora for this document (binaries built from `99c95fb`, the commit immediately before `ReportPosition`'s removal, so the census reflects the *before* state the optimization arc targeted):

| Corpus | Total static instructions | `ReportPosition` count | `ReportPosition` share |
|---|---|---|---|
| eraTHYMKR | 5,404,279 | 812,935 | **15.04%** |
| eramegaten_p_kr/Data | 6,249,981 | 896,068 | **14.34%** |

`ReportPosition` was a dedicated instruction, emitted once per compiled statement purely to keep `VmContext`'s `ScriptPosition` current for error messages and the debug console — no data flow, no control flow, nothing but bookkeeping — and it was the single largest or second-largest instruction category in both corpora (behind only `LoadStr`/`LoadInt`, ahead of `LoadVarRef`).

**Bigram/dispatch-order finding.** In both corpora, the pairs `ReportPosition -> LoadStr` and `ReportPosition -> LoadInt` are consistently among the top 5 most frequent bigrams out of 197-232 distinct pairs (eraTHYMKR: 7.76% and 5.69%; eramegaten: 9.18% and 4.61%). Summing every bigram with `ReportPosition` as its *first* element against `ReportPosition`'s own total count accounts for effectively all of it (eraTHYMKR: 812,934 of 812,935). This confirms `ReportPosition` was placed at the *start* of essentially every compiled statement, immediately preceding that statement's first data-load instruction — a producer sitting at a fixed, predictable point relative to statement boundaries, never interleaved mid-expression. That placement is exactly why an *on-demand, consumer-driven* replacement (§6) can recover the same information without a dedicated instruction: a statement boundary's line number is recoverable from the compiled body's own structure without the compiler having to say so explicitly on every step.

The census's own "simulated post-Priority-1" pass (filtering `ReportPosition` out of the bigram stream and joining its former neighbors directly) previewed this: `LoadStr -> LoadVarRef` becomes the single most common pair post-removal in both corpora (eraTHYMKR 14.56%, eramegaten 14.69%), and new direct edges appear where `ReportPosition` used to sit (e.g. `Goto -> LoadInt` at 4.76% in eraTHYMKR, `Call -> LoadStr` at 1.79% in eramegaten) — exactly the shape §6's design produces.

Category totals (eraTHYMKR, from the `99c95fb`-era census; `ReportPosition` counted under `pure` since it has no data/control dependency): `pure` 64.92%, `var_access` 14.94%, `control_local` 11.64%, `host` 7.49%, `control_call` 1.01%.

## 2. The A/B harness (`b006989`)

`jit_ceiling_bench.rs` (an existing file inherited from `llvm-jit`, repurposed here) compiles a fixed ERB loop and calls `TerminalVm::try_call` on it directly, 9 interleaved rounds per process, reporting min/median/max wall time. The loop body:

```
@BENCH
#DIM SUM
ISSKIP 1
LOCAL = 0
SUM = 0
WHILE LOCAL < {iters}
	IF LOCAL < {iters/2}
		SUM = SUM + LOCAL
	ELSE
		PRINTFORM iter {LOCAL}
	ENDIF
	LOCAL = LOCAL + 1
WEND
```

chosen (per §1's census) to mix variable reads/writes, arithmetic, a branch, and a `PRINTFORM` per iteration rather than one instruction type, so no candidate optimization could be mis-ranked by a benchmark that barely exercises the instruction it targets. `ISSKIP 1` keeps `Print`'s dispatch cost (pop, format, flag checks) in the mix without its `VirtualConsole` buffering cost swamping millions of iterations. No `black_box` is needed or used: `TerminalVm::try_call` is a real cross-crate call into a heap-backed interpreter that cannot be proven side-effect-free and elided — unlike the native-Rust comparison loop this file originally contained on `llvm-jit`, which needed `black_box` to avoid LLVM proving it closed-form (a mistake that once produced a bogus ~400,000,000× "speedup" there). A `dynamic_instruction_histogram` function computes exact (not sampled) per-type executed counts analytically, by walking the compiled body's own real `Goto`/`GotoIfNot` targets and multiplying by the known iteration split — this is the correctness guard used before and after every change in this document: if the histogram (minus whatever instruction the change legitimately removes) is not byte-for-byte identical, the change altered *what runs*, not just *how fast*, and any timing number is void until that is understood.

This benchmark's loop body source has not changed since `b006989`; only its diagnostic/histogram-printing internals evolved alongside the production code (Step 2 added a public `Instruction::ty()` discriminant, replacing Debug-string parsing; Step 3 removed `ReportPosition` from the printed breakdown). The workload itself is invariant, which is what makes the cumulative measurement in §8 possible using the *same* script across widely separated commits.

## 3. P0: dispatch chain to `match` (`e4723cf`)

`run_instruction` dispatched on `Instruction`'s payload type via a chain of up to 36 sequential `is_x()`/`as_x()` calls, each re-deriving the discriminant check every earlier call in the chain had already failed — instruction types positioned last in the chain (`LoadDefaultArgument`, `BuiltinCommand`, `BuiltinMethod`) paid the full linear scan on every dispatch. Fixed by making `InstructionType` public and adding `Instruction::ty()` (`#[inline(always)]`, no encoding change, no `VERSION_MAGIC` bump), then converting the chain to `match inst.ty() { ... }` with one arm per variant (40 variants, no wildcard — the compiler now rejects a future instruction type added without a dispatch arm, where the old chain would have silently fallen through to dead-code `unreachable!`).

Correctness guard: histogram byte-identical at iters=10 and iters=3,000,000 (the refactor changes only *how* an instruction is selected, never which one runs). `cargo test --workspace`: 450 passed, 0 failed.

Measurement (5 interleaved pairs, baseline binary preserved before rebuilding "new," alternating within one batch, 3,000,000 iterations): all 5 pairs faster, deltas -253.2/-128.3/-116.6/-77.7/-57.0ms (min basis). Median pair delta **-116.6ms (-6.4%)**, strongest pair delta **-253.2ms (-12.9%)**; every pair agreed in sign, effect well above this box's ~8.7% same-build noise floor.

## 4. `index_local_var`'s two-part fix (`99c95fb`)

Found while investigating dispatch cost further: `VariableStorage::index_local_var`, on the hot `LoadVarRef`/`StoreVar` path for every `#DIM`-declared local access (`LOCAL`, `ARG`, any user `#DIM` — far more common than character-indexed global array access), had two stacked defects:

1. `self.read_int("TARGET", &[])?` resolved the literal `"TARGET"` through `impl StrKeyLike for &str`, calling `interner().get_or_intern(self)` — a full hash, lock-protected shard read, and arena probe — on *every single call*, to re-derive a key `index_var` (two functions up in the same file) already had sitting in a fixed `known_key` lookup table. Fixed by using `self.known_key(KnownVariableNames::Target)`.
2. That read was unconditional, but `target` is only consumed inside the `UniformVariable::Character` arm when `calculate_single_idx` returns `None` (an omitted index on a character-indexed local) — every `Normal`-variable access (the overwhelming majority: plain `#DIM` scratch variables are never character-indexed) paid the read and discarded the result. Fixed by peeking `VariableInfo::is_chara` and the index shape immutably first (new `LocalVarTable::get`, mirroring the existing `get_mut`), calling `read_int` only when a `Character` local's index is actually omitted.

Correctness guard: histogram byte-identical at iters=10 and iters=3,000,000 — this change alters no instruction *selection*, only what a couple of instructions' handlers do internally. `cargo test --workspace`: 450 passed, 0 failed.

Measurement, isolating the two fixes with a paired-interleaving protocol (5 rounds; the benchmark's `LOCAL`/`SUM` are both `Normal`, non-character, so fix 2 alone would already skip the read entirely for this workload — isolating fix 1's effect required a temporary `known_key`-but-still-eager variant, "variant A," measured once for this purpose and discarded, never committed):

| Comparison | Median | Min | Sign agreement |
|---|---|---|---|
| baseline → `known_key` only (variant A) | -231.8ms (-12.64%) | -413.2ms | 5/5 negative |
| `known_key` → +lazy read (both fixes) | -136.2ms (-8.50%) | -186.7ms | 5/5 negative |
| baseline → both fixes combined | -370.7ms (-20.06%) | -511.3ms | 5/5 negative |

Both components are separable and both matter: the interner-cost fix is the larger of the two, but the wasted eager read is a genuine second effect on top of it, not noise.

## 5. Step 3, attempt 1: lockstep per-instruction stamping (discarded, never committed)

The first design for removing `ReportPosition` kept `ctx.update_position` current by stamping a line on *every* instruction step: a `positions: Vec<(u32, u32)>` side table (pc → line, monotonic in pc) was added to `FunctionBody`, and `run_body`'s main loop walked `advance_position`/`seek_position` in lockstep with the instruction cursor, updating `ScriptPosition` unconditionally before every single dispatch.

Measured 5/5 rounds *slower*: **median +8.024ms (+0.64%), min +4.956ms (+0.40%)**, 3,000,000 iterations. Small in relative terms, but unambiguous and consistent in sign — a regression, not noise.

**Root-cause mechanism** (recorded here explicitly so it is not rediscovered expensively): `ReportPosition` cost one dispatch on a *conditional* ~13.5-15% of steps (§1). The lockstep stamp replaced that with a position-table lookup plus an `Option`-taking bookkeeping call on *literally 100%* of dispatches — itself almost as expensive per-call as the instruction it eliminated (same side table, same kind of write into `VmContext`), just paid unconditionally instead of conditionally. Trading a conditional ~13.5% cost for an unconditional 100% cost of comparable per-call weight is a net loss by construction, regardless of how cheap the individual lookup is made — the win from eliminating an instruction from the dispatch stream is only real if its replacement is paid on a **narrower** set of dispatches than the original, never a wider one. This is the trap: "the instruction is gone, so it must be faster" does not follow if what replaced it runs more often than the instruction did.

## 6. Step 3, attempt 2 (v2): on-demand, consumer-driven stamping (committed as `d0f1162`)

v2 instead stamps `ScriptPosition` only at the small set of points where a stale position could actually be *observed* — consumer-driven rather than producer-driven. An exhaustive audit of the codebase found exactly two position *consumers*: `debug_console::show_debug` and `TerminalVm::start`'s error-unwind print loop. Every point that could change what either of those would read is a stamp site; nothing else needs one.

- `erars-bytecode/src/lib.rs`: kept the `positions` side table from attempt 1 (it was never the problem — the *unconditional per-step read* was) as the lookup backing store, serialized via `write_arr!`/`read_arr!` in `FunctionBody`'s own encoding. `VERSION_MAGIC` 11 → 12.
- `erars-vm/src/function.rs`: replaced the lockstep `advance_position`/`seek_position` pair with one stateless accessor, `FunctionBody::line_at(&self, cursor: u32) -> Option<u32>` — binary search (`partition_point`) over the side table, no mutable walk state to keep synchronized with the cursor:

  ```rust
  pub fn line_at(&self, cursor: u32) -> Option<u32> {
      let idx = self.positions.partition_point(|&(pc, _)| pc <= cursor).checked_sub(1)?;
      Some(self.positions[idx].1)
  }
  ```

- `erars-vm/src/terminal_vm/executor.rs`: `run_instruction` and `run_builtin_command` both gained `cursor: u32, body: &FunctionBody` trailing parameters. A `stamp_position!(ctx, body, cursor)` macro (`if let Some(line) = body.line_at(cursor) { ctx.update_position(...) }`) is called at exactly 11 sites found by the consumer audit: before every `ctx.input_redraw` (`Print`+`WAIT`, `Twait`, `Wait`/`WaitAnykey`/`ForceWait`, the `Input` family), before `TryCall`/`TryJump`'s `vm.try_call`, before `Jump`/`Call`'s `vm.call`, before `CallEvent`'s `call_event!`, before `DoTrain`/`CallTrain`'s `run_call_train`, before `LoadData`'s `run_load_data`, before `SaveGame`'s `run_save_game`, before `LoadGame`'s combined load block. `run_save_game`/`run_load_data`/`run_call_train`/`run_train_commands`/`run_load_game` keep unchanged signatures — none of them push their own call-stack frame, so one stamp at their `run_builtin_command` dispatch site covers their entire internal excursion.
- `erars-vm/src/terminal_vm.rs`: `run_body` captures `let my_depth = ctx.call_stack().len();` right after `call_internal` pushes its frame; its `Err(err) => { ... }` arm stamps a line via `body.line_at(cursor as u32)` **only if** `ctx.call_stack().len() == my_depth`, before returning the error. Without this guard, an error thrown at call depth N+2 and propagated back through N+1 and N would get re-stamped with N+1's and then N's own cursor on the way out, silently discarding the innermost frame's true position — a correctness bug that would only manifest on a nested-call error path, easy to miss without deliberately reasoning about re-propagation.
- `erars-lint/src/lib.rs` (`check_variable_exist_inner`): migrated to `func.line_at(0).unwrap_or(1)` / per-instruction `func.line_at(i as u32)` — stateless calls are acceptable here since lint is a cold, one-time pass, not the hot interpreter loop.
- `erars-compiler/src/{compiler,instruction,parser}.rs`: `ReportPosition`/`report_position` removed outright — no instruction encodes a line number into the stream any more; the side table is now the only place line information lives.

**Correctness guard**, three layers: (1) `jit_ceiling_bench`'s histogram byte-identical for every instruction other than `ReportPosition`, at iters=10 and iters=3,000,000; (2) re-confirmed at real-corpus scale via `jit_census` — on both eraTHYMKR and eramegaten, every non-`ReportPosition` row's raw count is identical between `99c95fb` and `d0f1162`, only `ReportPosition`'s row disappears (§7); (3) both oracle fixtures (`tests/run_tests/basic/debug_console_window.out`, `tests/run_tests/control_flow/unbound_ref.out`) pass verbatim. `cargo test --workspace`: 451 passed, 0 failed.

**Measurement**: 10 interleaved rounds (5 old-first + 5 new-first, to rule out ordering bias), 3,000,000 iterations each. Deltas (NEW−OLD, ms): -81.428, -64.515, -22.149, -43.170, -70.395, -52.882, -86.371, -48.257, -82.303, -63.284. **10/10 sign agreement**, NEW always faster. Median -63.9ms (-5.1%), weakest effect -22.1ms (-1.8%), strongest -86.4ms (-6.8%). Load average rose 0.82 → 2.50 during the batch (another user on the box mid-run); noted for transparency — does not change the sign-agreement conclusion, since the effect holds under both interleave orderings and exceeds same-build noise by a wide margin.

## 9. `index_var`'s global-path TARGET fix (`1d5a8df`)

`VariableStorage::index_var` — the *global*-variable counterpart of §4's `index_local_var` (`FLAG`, `CFLAG`, `TALENT`, and every other character/global array, which dominate real game logic far more than `#DIM` locals do) — had the identical defect class as §4's fix 2: it unconditionally read `TARGET` via `self.read_int("TARGET", &[])?` before checking whether the access was even character-indexed, discarding the read on every `Normal`-variable access (the overwhelming majority). Fixed the same way: peek `self.variables.get(&name)` (a plain `HashMap::get`, no new accessor needed) for `is_chara && calculate_single_idx(args).0.is_none()` before conditionally reading `TARGET` via `known_key`. `TARGET`'s own `VariableInfo::is_chara` is `false`, so the recursion guard the original code carried (`name != target_key`) is now provably unreachable and was removed.

**No timing number is claimed for this fix.** `jit_ceiling_bench`'s loop body (§2) only ever touches `LOCAL` and `SUM`, both `#DIM` locals — it never exercises `index_var`'s global path at all, so this fix is completely invisible to every synthetic measurement in this document. The histogram-identity correctness guard (byte-identical at iters=10 and iters=3,000,000) is therefore trivially true here, not meaningful evidence that the fix does anything — it is meaningful only in that it confirms the fix broke nothing the benchmark *does* exercise. This gap is exactly why §11's real-workload replay exists: a real game's actual `FLAG`/`TALENT` access pattern is precisely what this fix targets, and no synthetic loop in this document was ever going to see it. `cargo test --workspace`: 451 passed, 0 failed (unchanged from §6, no test count regression).

## 10. The `get_or_intern` 11.19% cost: resolved by §4, confirmed absent post-fix

## 12. Measurement protocol (for reproduction/audit)

Every A/B number in this document follows the same rules:

1. **Build every binary variant first**, into distinct paths (e.g. `/tmp/bench_x_old/bin`, `/tmp/bench_x_new/bin`), before any timing run begins — never rebuild mid-comparison.
2. **Interleave, don't block.** Run old/new alternately within one batch (never all-old-then-all-new), and for the more consequential comparisons (§6, §8) run the alternation in *both* orders (5 old-first + 5 new-first = 10 total) to rule out any first-run/thermal/scheduler ordering bias.
3. **Report per-round deltas, then min/median**, not just an aggregate. Every comparison in this document states its sign agreement explicitly (e.g. "10/10 rounds negative") — a real effect must hold under every round and both interleave orders, not just on average.
4. `uptime` before and after each batch, to flag (not silently absorb) load-average contamination from other processes on the box — see §6's noted load spike, which did not change the conclusion because the effect size and sign agreement held regardless.
5. **Correctness guard precedes every timing claim.** `BENCH_DEBUG=1 <binary> <iters>` dumps the compiled instruction stream and the analytically-computed dynamic histogram; compare old vs new with `diff` on the full histogram output (or, for corpus-scale checks, on `jit_census`'s full "Instruction census" section), never by eyeballing a handful of top rows. A change is only "faster," not "different," once every row outside the one(s) the change legitimately touches is confirmed byte-for-byte identical.
6. Reproduction commands used throughout:
   - `cargo build --release -p erars-loader --example jit_ceiling_bench` (per commit/worktree, into a distinct `target/` via `git worktree add /tmp/<name> <commit>`)
   - `<binary> 3000000` for a timing round; `BENCH_DEBUG=1 <binary> 10` for the correctness-guard dump
   - `cargo build --release --features multithread -p erars-loader --example phases --example jit_census` for the corpus tools; `phases <game-dir> <rounds>`, `jit_census <game-dir>`
   - `erars-stdio <game-dir> --save --quite` for the `game.era` on-disk size measurement (`run_script` only loads/compiles/lints and returns before any game loop starts, confirmed non-interactive and safe to script)
   - `erars-stdio <game-dir> --quite --load --bench-timing --use-input <ron-file> --exit-when-input-exhausted < /dev/null` for §11's real-workload replay (requires a version-matched `game.era` already saved via `--save` from the *same* binary); `--features inst-counter` to additionally dump the dynamic instruction histogram
7. **Real-corpus replay (§11, §14) is not deterministic run-to-run; the corpus's own static census is.** Discovered while validating §14: re-running the *same unmodified binary* against the *same* real THYMKR replay script twice produces dynamic instruction-dispatch counts that differ by single-digit-to-tens on rows in the hundreds-of-thousands (e.g. `LoadVarRef`'s dispatch count varied by ~6 out of ~375,000 across two runs of one binary) — a real game's `RAND`-driven branches take different control-flow paths on different runs, even with an identical fixed input-action script, because `RAND`'s own output differs run to run. This means a real-replay dynamic histogram is a *qualitative* correctness signal ("does this look right, and is the loss/gain of dispatches roughly what the change should produce"), never a byte-exact one — unlike `jit_ceiling_bench`'s synthetic loop (§2), which contains no `RAND` and *is* byte-exact deterministic, so §3/§4/§6/§8's histogram-diff guards remain fully valid as stated. For a real-corpus change's byte-exact correctness guard, use `jit_census`'s **static** instruction census (deterministic — it counts what the compiler emitted, not what a run happened to execute) and diff its full output, the same as item 5 above already does for corpus-scale checks; reserve the dynamic real-replay histogram for the qualitative check and for timing measurement only.

## 14. P2: fusing `LoadStr` → `LoadVarRef` into one instruction

**Finding.** `LoadVarRef` (§1: eraTHYMKR's third-largest static category behind `LoadStr`/`LoadInt`) pops a variable-name `StrKey` pushed by a dedicated `LoadStr` immediately beforehand, plus `count` index-argument values already on the stack from evaluating the variable's own subscripts — the same call/consumer relationship §1/§6 already found and exploited for `ReportPosition`. A new corpus-loading tool, `crates/erars-loader/examples/loadvarref_census.rs`, confirms the relationship is not incidental but universal: every `LoadVarRef` occurrence in both real corpora is immediately preceded by exactly one `LoadStr` of its own variable name, with **zero** exceptions.

| Corpus | `LoadVarRef` occurrences | `LoadStr`-immediately-precedes | `count=0` | `count=1` | `count=2` | `count=3` | max `count` | interner len |
|---|---|---|---|---|---|---|---|---|
| eraTHYMKR | 666,588 (14.52% of 4,591,344 static insts) | **100.0000%** | 161,655 (24.25%) | 471,019 (70.66%) | 33,914 (5.09%) | 0 | 2 | 53,639 |
| eramegaten_p_kr/Data | 768,238 (14.35% of 5,353,913 static insts) | **100.0000%** | 415,795 (54.12%) | 183,284 (23.86%) | 167,834 (21.85%) | 1,325 (0.17%) | 3 | 197,865 |

**Design rejected: packing `count` into the 4-byte instruction payload.** `Instruction` (`erars-compiler/src/instruction.rs`) is a fixed 1-byte discriminant plus a 4-byte `data` payload — 5 bytes total, unchanged since before this arc. A first design attempt tried to fit a fused `{name: StrKey, count}` entirely inside that 4-byte payload: `StrKey` is a full, unmodified 32-bit value (`erars-ast`'s identifier interner has `ID_CAP = 4_000_000`, needing 22 of those 32 bits; `erars-ast/src/literal_store.rs`'s `LIT_BIT = 1<<31` reserves a further bit to distinguish literal-store keys, though `Variable.var` — confirmed via every `get_or_intern` call site feeding it in `erars-compiler/src/parser.rs` — is always identifier-interner-sourced, never literal-store), so packing even 2 bits of `count` alongside it would require either truncating `StrKey` (silently wrong the moment the interner's key space grows past whatever headroom was assumed, a defect that would not surface until a corpus large enough to hit it existed) or coupling the encoding to `ID_CAP` in a way nothing else in the codebase does. This was the wrong place to look for room and was rejected before implementation.

**Design adopted: spend discriminant space instead.** `InstructionType`'s discriminant is a separate, 1-byte budget from the 4-byte payload — around 216 of its 256 possible `u8` values are unused. `count` only ever takes 4 distinct values across both real corpora (0-3, per the table above), needing 2 bits, so it fits as 4 new discriminants rather than as packed payload bits: `LoadVarRefNamed0 = 26, LoadVarRefNamed1 = 27, LoadVarRefNamed2 = 28, LoadVarRefNamed3 = 29` (inserted between the existing `StoreResult = 25` and `Call = 30`), each carrying an **unmodified, lossless, full 32-bit `StrKey`** as its payload — the same payload `LoadStr`/`LoadVarRef` already carried separately, just now living on one instruction instead of two. This costs exactly 4 of the ~216 free discriminant values, has zero coupling to `ID_CAP` or any other interner-size assumption, and leaves `Instruction`'s own size and layout completely unchanged (still 5 bytes). `count > 3` (unobserved in either corpus but reachable by a source program with a deeply-subscripted variable — e.g. explicit `#DIM name, a, b, c, d` gives 4 index arguments) falls back unchanged to the classic two-instruction `LoadStr` + `LoadVarRef(count)` form; this is real, tested, reachable code, not a documented-but-dead escape hatch (see Test coverage below). The two designs are worth contrasting explicitly: the rejected one saves nothing (the payload was going to be spent on `StrKey` either way) while introducing a silent-truncation failure mode with no test that could ever catch it short of growing a corpus past the assumed headroom; the adopted one spends a resource (discriminant space) this arc had never touched before and stays exact under every input the type system allows.

**Implementation.** `push_var_ref` (`erars-compiler/src/compiler.rs`) — previously `Instruction::load_str(var.var)` unconditionally followed by `Instruction::load_var_ref(count)` on the non-extern path — now matches `count`: `0..=3` emits the corresponding single `load_var_ref_namedN(var.var)` instruction (the `define_instruction!` macro's `@StrKey` group auto-generates the constructor/`is_`/`as_` triplet per variant from the four new `(load_var_ref_namedN, LoadVarRefNamedN)` entries); anything else still pushes `load_str` then `load_var_ref(count)`. The extern-varref path (`var.func_extern.is_some()`, two `LoadStr`s feeding `LoadExternVarRef`) and `Expr::Method`'s call-argument shape are both untouched and explicitly out of scope — the census above measured only the plain-variable path. `erars-vm/src/terminal_vm/executor.rs`'s `run_instruction` — the codebase's only exhaustive `match` on `InstructionType`, no wildcard arm, so a missing variant is a compile error rather than a silent fallthrough — gained 4 arms immediately after the existing `LoadVarRef` arm, each taking the named `StrKey` directly (no interning, no lookup) and calling `ctx.take_arg_list(Some(name), N)?` / `ctx.push_var_ref(name, func_name, args)?` with `N` the literal count. `jit_census.rs`'s `category()` classifier was updated to bucket `LoadVarRefNamed0..3` under `"var_access"`, alongside `LoadVarRef` — otherwise it panics on an uncategorized variant when pointed at post-fusion bytecode. `VERSION_MAGIC` bumped `[2,3,2,3,0,0,0,13]` → `[2,3,2,3,0,0,0,14]`: an older reader has no `LoadVarRefNamedN` case in its own dispatch and would either reject or misparse the new discriminant values, so the bump forces the existing clean-rejection path.

**Correctness guard: an exact static-census arithmetic identity, both corpora.** `jit_census`'s full unigram/bigram/category output was diffed between a pre-fusion worktree (`git worktree add /tmp/erars_p2_before 26049cb`) and the post-fusion tree. ## 15. Post-P2 corrections: the W1001 lint regression, the `rmp_serde` depth limit, and the eramegaten `RAND` crash resolved

Three follow-ups, all found or requested after §14 landed, none of which involved reopening §14's fusion design itself.

### 15.1 The W1001 lint regression P2 shipped silently

**The bug.** `erars-lint`'s "variable does not exist" check (`check_variable_exist_inner`) only recognized the classic `LoadStr` immediately followed by `LoadVarRef` — reading the variable's name from `func.body()[i - 1]`. §14's fusion eliminates that exact adjacency for every case it applies to (per §14's own census table, **100.0000%** of real `LoadVarRef` occurrences in both corpora), so after §14 the lint's `if inst.is_load_var_ref() { .. } else { continue }` dispatch simply never matched a real reference again — not a crash, not a warning, just silent, complete non-detection. §14's own correctness guard (an exact static-census arithmetic identity) could not have caught this: it verifies instruction *counts* round-trip, and a lint pass over those instructions is a different question the guard was never asking. Confirmed on the real corpus, not just reasoned about: `erars-stdio <eramegaten-dir> --save --quite`'s W1001 output was **9** warnings on a pre-fusion (`26049cb`) binary and **0** on the fusion-only, pre-fix (`454fb16`) binary — the regression is real and total, not partial.

**The fix.** `check_variable_exist_inner` now matches on `inst.ty()`: `InstructionType::LoadVarRef` keeps the old `body()[i - 1]`-as-literal-string path unchanged; the four new `LoadVarRefNamed0..3` variants read the name directly from the instruction's own payload via `as_load_var_ref_named{0,1,2,3}()` (no adjacent instruction involved at all); `LoadExternVarRef` is untouched. This is the fix the fused shape actually needs — not "look one instruction further back," but "the name is no longer a separate instruction to look back at."

**Audit: every other consumer of the old adjacency, found by grep, not by trusting a candidate list.** Searched the whole repository for `is_load_var_ref\(\)|as_load_var_ref\(\)|is_load_str\(\)|as_load_str\(\)` and separately for the word-bounded `InstructionType::LoadVarRef\b` (to catch a match arm that only handles the classic variant). Four hits, all accounted for: `erars-lint/src/lib.rs` (fixed above); `erars-loader/examples/loadvarref_census.rs`, a diagnostic census tool that intentionally measures the pre-fusion adjacency pattern and is correct left as-is; `erars-vm/src/terminal_vm/executor.rs`, the runtime dispatcher, which has handled both the classic and all four fused forms correctly since §14 itself shipped; `erars-vm/tests/loadvarref_named_fusion.rs`, whose own assertions are already fusion-aware. `debug_console.rs` — floated as a plausible candidate before checking — greps clean: zero matches on any of `is_load_var_ref|as_load_var_ref|is_load_str|as_load_str|LoadVarRef|LoadStr`, so it was never actually a consumer.

**Regression test.** `crates/erars-lint/tests/w1001_fused_var_ref.rs` (new) plus a fixture `crates/erars-lint/tests/LINT_TEST.ERB` declaring `A0`/`A1` and referencing them alongside undeclared `UNDECLARED0`/`UNDECLARED1` (count 0 and 1 respectively). The test first asserts the compiled function actually contains 2 `LoadVarRefNamed0` and 2 `LoadVarRefNamed1` instructions and zero classic `LoadVarRef` — so it cannot pass via an accidental classic-path fallback — then asserts `check_function` fires exactly 2 W1001 diagnostics, naming `UNDECLARED0`/`UNDECLARED1` and never `A0`/`A1`. Confirmed this actually defends the fix: `git stash push -- crates/erars-lint/src/lib.rs` (keeping the new test, reverting only the fix) makes the test fail with `left: 0 right: 2, got: []` — exactly the shape of the real regression — then `git stash pop` restores the fix.

**Full re-verification against the pre-P2 baseline, both corpora, diff empty.** Built `/tmp/p2_before/erars-stdio` (`26049cb`, pre-fusion) and a fresh binary from the lint-fixed working tree; ran both as `<binary> <dir> --save --quite < /dev/null` (this path lints and returns before any game loop starts — confirmed non-interactive and safe, per §13 item 6) against fresh copies of eraTHYMKR and eramegaten, capturing stderr. eraTHYMKR: 0 diagnostics on both binaries (a clean corpus). eramegaten: **W1001 = 9 on both binaries**, and `diff` on the full sorted diagnostic output (142 lines each) is identical in content — the only difference is the temp-copy directory name embedded in printed file paths (`/tmp/lint_megaten_before/…` vs `/tmp/lint_megaten_after/…`), the same kind of path-prefix noise this document's other corpus-copy comparisons already discount. The fix restores the pre-fusion lint output exactly.

### 15.2 The `rmp_serde` depth-limit bug: fixed, with a cap that is actually measured against the stack budget it claims to guard

§12 already found that eramegaten's `--load` path fails independently of the u16 line-encoding fix, on both sides of it, with `Failed to load <path>: depth limit exceeded`. The cause, read directly from `rmp-serde-1.1.2`'s own source (`~/.cargo/registry/…/rmp-serde-1.1.2/src/decode.rs`): `Deserializer::new`/`from_read_ref` default `depth: 1024` (lines 211, 289), decremented once per nesting level entered (the `depth_count!` macro, lines 49-61) — a maximum-*simultaneous*-nesting guard, not a total-node-count one, so it is triggered by deeply *chained* structures. `HeaderInfo`'s `VariableInfo::init: Option<Box<[Expr]>>` is exactly such a structure: a long left-associative `#DEFINE`/`#DIM` initializer (`a + b + c + …`) nests one serde level per term through `Expr`'s recursive `Box` fields.

**Encode side checked, found unaffected.** `encode.rs`'s `Serializer` also carries a `depth: 1024` field and a `#[doc(hidden)] pub fn unstable_set_max_depth` explicitly commented "Currently unused" — grepping `encode.rs` for any read of `self.depth` or a `DepthLimitExceeded` return site finds none outside the `Error` enum's definition and `Display` impl. The field exists but nothing in the serializer ever checks or decrements it; `--save` has no enforced depth limit at all, consistent with this arc's many successful large `--save` runs against eramegaten throughout §7/§12/§14.

**How deep the real corpus actually needs, measured, not guessed.** An initial version of this fix raised the cap to `1 << 20` (1,048,576) and its own comment claimed this "fails cleanly... rather than recursing until the native call stack overflows" — that claim was never checked and turned out to be false (see below). Measured properly instead, two ways:

- `crates/erars-loader/examples/expr_depth_probe.rs` (new): compiles the real corpus through the actual `run_script` path (never `--save`, so read-only against the corpus) and walks every `VariableInfo::init` in both `HeaderInfo::global_variables` and every function's local variable table, computing `Expr` AST nesting depth. Result against real eramegaten: 872 initializers total; the deepest, `SEIZON_パーツデータ`, nests 2466 `Expr` levels — the next-deepest, `KAORU_パーツデータ`, is only 233, a >10x cliff, so this one variable is genuinely the corpus's outlier, not a sign the whole corpus runs this deep.
- `crates/erars-loader/examples/depth_cap_probe.rs` (new): loads that real corpus's actual `game.era` bytes and binary-searches `set_max_depth` directly, rather than assuming how many `rmp_serde` depth units one `Expr::BinopExpr` level costs. Result: the minimum working depth is **2471** — 5 above the AST-measured 2466, confirming the AST depth maps almost exactly 1:1 onto `rmp_serde`'s own counter (the small constant difference is the outer `(HeaderInfo, HashMap<...>)` envelope).

**How deep is actually safe on the real runtime thread, also measured, not guessed.** `erars-stdio`'s real runtime thread is built with `.stack_size(8 * 1024 * 1024)` (`crates/erars-stdio/src/main.rs`) — an 8 MiB budget, not the far larger default OS stack some other thread might get. A depth cap is a stack-exhaustion guard, so its safety has to be measured against *that* budget, not assumed from a per-level byte estimate. `crates/erars-loader/examples/depth_stack_crash_probe.rs` (new) builds a synthetic `Expr::BinopExpr` chain of a given depth, serializes it (unbounded, confirmed above), and deserializes it on a thread built with that exact same 8 MiB stack size, one depth per process (a stack overflow is a fatal signal, not a catchable `Result`, so looping depths in one process would take every later candidate down with an earlier crash). Bisecting: a **release** build survives up to depth ~21,600 before the thread reports "has overflowed its stack" at ~21,800; a **debug** build, with less-aggressively-inlined recursion, only survives up to ~12,000 before overflowing at ~14,000. `1 << 20` was never a "fails cleanly" bound — it is roughly **48x past** the point where the process segfaults first, meaning the actual failure mode for a corrupted or adversarially-deep file was a segfault, not the clean `depth limit exceeded` error the cap's own comment claimed to still provide.

**The fix**, at `erars-loader/src/lib.rs`'s `load_script`: replaced the one-shot `rmp_serde::decode::from_read(&mut file_bytes)?` with an explicit `let mut de = rmp_serde::Deserializer::new(&mut file_bytes); de.set_max_depth(4096); serde::Deserialize::deserialize(&mut de)?`. `4096` is chosen with a shown margin on both sides: ~1.7x above the measured real-corpus requirement (2471), to leave room for organic corpus growth, while staying ~3x below the measured debug-build crash point (~12,000) and ~5x below the measured release-build one (~21,600), leaving headroom for slower platforms or more heavily-instrumented builds that spend more stack per recursion level than either build measured here. If a future corpus genuinely needs deeper nesting than this, the correct fix is an iterative (de)serializer for `Expr`, not raising this constant again without re-measuring. Added `serde.workspace = true` to `erars-loader/Cargo.toml` (needed for the explicit `Deserialize::deserialize` call; `rmp_serde` does not re-export the trait).

**Verified fixed**: `erars-stdio <eramegaten-dir> --quite --load --bench-timing --use-input <empty-ron> --exit-when-input-exhausted < /dev/null` no longer reports `depth limit exceeded` — it now runs into the game loop and reaches §15.3's `RAND` crash instead, which is exactly the previously-blocked failure mode becoming reachable.

**Verified pre-existing against the actual `35435b9` baseline directly, not inferred from branch binaries.** Earlier framing of this bug (§12) inferred "pre-existing and unrelated" from two already-modified branch binaries; that inference was not checked against the real baseline and the user correctly declined to accept it as fact. Checked properly this time: built `35435b9` fresh in an isolated `git worktree`, had that unmodified binary `--save` eramegaten's own corpus and then `--load` its own output with itself — same binary on both ends, no cross-version bytecode-format question involved. It fails identically: `Failed to load <path>: depth limit exceeded`. The bug predates this entire arc and is unrelated to items 1-3's changes.

### 15.3 The eramegaten `RAND` crash: root cause traced and confirmed, not an engine bug

§11's original text guessed the cause was "plausibly a `WINDOW_WIDTH`-style value defaulting to 0 headlessly," without checking the ERB source. That guess was wrong (§13's methodology note, third instance). Traced directly this session:

`PRINT_TITLE.ERB:38-67` loops `LCOUNT` over `TITLE_LIST` (`VARSIZE` = `TITLE_PICTURE_NUM * 5` = 500). Each iteration: `TRYCCALLFORM IS_TITLE_USEABLE_{LCOUNT}` gates on a per-index function that, when it exists, returns a save-state-dependent usability flag (`G_USEABLE_TITLE_PICTURE:N`, e.g. index 0 requires a specific companion character to have joined — never true on a fresh run); when no `IS_TITLE_USEABLE_N` function exists for that index (confirmed: only indices 0, 1, 2, 23, 24, 25, 26 define one, out of 500), `TRYCCALLFORM`'s `CATCH` sets `L_PRIORITY = 1` and the index proceeds unconditionally. Surviving indices then hit `:50`: `SIF !GCREATEFROMFILE(GID, "タイトル画像\タイトル" + TOSTR(LCOUNT, "000") + ".webp") : CONTINUE`, and only a successful `GCREATEFROMFILE` increments `CNT_TITLE_PICTURE` (`:59-60`). Line 67: `TITLE_NO = TITLE_LIST:(RAND:CNT_TITLE_PICTURE)` — `RAND` rejects a non-positive argument, which is Emuera's own behavior too, not an erars-specific restriction.

**Distinguishing the two candidate causes named going in — both false.** (a) *Headless stub returning failure unconditionally*: false. `GCreateFromFile`'s executor arm and `graphics.rs`'s implementation do a real `image::ImageReader` decode and a real filesystem check; there is no stub. (b) *Missing backslash-to-`/` path translation*: false, and already fixed independently of this session — `content_path` (`erars-vm/src/terminal_vm/executor.rs:1178-1193`) explicitly translates `\` to `std::path::MAIN_SEPARATOR` on non-Windows, with a comment that names this exact game's `"タイトル画像\\タイトル001.webp"` literal as the motivating case.

**The actual cause: this checkout ships no title-image assets at all.** `Data/resources/` does not exist in this checkout (`ls` confirms; the repository's own `.gitignore` lists `/Data/resources`), and `追加画像について.MD` at the repo root points at an external download the checkout has not performed. `GCREATEFROMFILE`'s real, correct file-existence check therefore fails for every one of the 500 possible indices, `CNT_TITLE_PICTURE` never leaves 0, and `RAND:0` is a genuine script-level error condition — not an erars defect, headless or otherwise. This matches a pre-existing, independently-reached finding already on record in `docs/research/2026-09-03-emuera-command-gap.md` (its §"eramegaten `RAND` crash" note, itself confirmed there by supplying one asset).

**Re-confirmed this session with a fresh, controlled reproduction.** Created a synthetic 64×64 WebP at `resources/タイトル画像/タイトル003.webp` in a scratch copy of the corpus. Index 3 was chosen deliberately: it is one of the 493 indices with no `IS_TITLE_USEABLE_N` override, so `TRYCCALLFORM`'s missing-function `CATCH` makes it unconditionally usable, unlike indices 0-2/23-26's save-state-gated flags (an initial attempt at index 0 confirmed this the hard way: it stayed at `RAND:0` even with an asset present, because `G_USEABLE_TITLE_PICTURE:0` requires a companion character no fresh run has). With `タイトル003.webp` present, the exact same `--load --use-input <empty> --exit-when-input-exhausted` invocation that previously crashed now completes `PRINT_TITLE` and reaches the interactive title menu — `[0] ＮＥＷ ＧＡＭＥ` / `[1] ＬＯＡＤ ＧＡＭＥ` — with no VM error anywhere in the run.

**Conclusion: nothing to fix in erars for this crash.** It is a missing-corpus-asset condition specific to this checkout, reproducible in the real Emuera/.NET engine for the same reason, not a headless-frontend limitation and not a path-resolution bug — both of the plausible engine-side explanations were checked directly against the code and ruled out before concluding this. To state this unambiguously for anyone reading this document later: `Data/resources/` does not exist in this checkout, so `content_path()` returns `None` (equivalently, `GCREATEFROMFILE` reports failure) for every one of the 500 title images, by direct and correct consequence of the missing directory, not a bug in `content_path()`, `GCreateFromFile`, or anywhere else in erars; `RAND:0` is the legitimate downstream result, and Emuera would raise the identical error given the identical missing corpus. Of this item's two findings, exactly one is a genuine erars engine defect — §15.2's `rmp_serde` depth cap, now fixed. This one, §15.3, is not an engine defect of any kind; no code change is warranted or implied by it.

15.1 and 15.2 land as their own commits (`crates/erars-lint/{src/lib.rs,Cargo.toml,tests/w1001_fused_var_ref.rs,tests/LINT_TEST.ERB}`; `crates/erars-loader/{src/lib.rs,Cargo.toml}` respectively), separate from §14's `454fb16`. 15.3 is an investigation with no code change: the two candidate engine-side causes named at the outset were both checked and ruled out, and the actual cause is outside erars's scope to fix.

## 16. eramegaten real-gameplay dynamic histogram, and four engine defects found driving it there

§11 excluded eramegaten from the dynamic-histogram measurement because it crashed at its own title screen; §15.3 traced that specific crash to a missing corpus asset, not an engine bug, and unblocked the title screen with a synthetic image. Driving *past* the title screen into real gameplay (character creation → role selection), for a second, independent corpus's dynamic histogram to compare against §11/§14's eraTHYMKR baseline, surfaced four further, unrelated defects — three narrow enough to fix and test within this session (all three committed in `96d1167`); the fourth is a materially larger, previously wholly-unimplemented Emuera assignment form, documented here and deliberately left for a dedicated future session rather than rushed.

**Setup.** A scratch copy of `eramegaten_p_kr/Data` (`/tmp/megaten_scratch`, never the read-only original) with `resources/タイトル画像/タイトル003.webp` synthesized as in §15.3, so the title screen resolves. Driven via `--use-input <ron> --exit-when-input-exhausted` through: disclaimer → new game → options → extra-content toggle → gender/body/orientation/experience → detail-setup skip → job-change skip → the six-class role-selection menu.

### 16.1 Three defects found and fixed

1. **`SPLIT` never set `RESULT`.** Emuera's reference doc for `SPLIT` states the split count is written to `RESULT`; callers rely on it (e.g. `RAND:RESULT` to pick a random split element). Fixed in `run_builtin_command`'s `Split` arm.
2. **`EXISTFUNCTION(name)` was entirely unimplemented**, falling through to a dynamic user-function-call attempt that crashed with "... is not exists" for any non-callable name. Added `BuiltinMethod::ExistFunction` (0 = absent/system-builtin, 1 = normal `@`-function, 2 = `#FUNCTION`, 3 = `#FUNCTIONS`, matching Emuera's documented return values), appended to the enum tail (no `VERSION_MAGIC` bump needed — `BuiltinMethod` serializes by variant name). **Gotcha confirmed the hard way**: `game.era` caches compiled bytecode, so a save compiled *before* this fix keeps calling the old dynamic-call fallback even after the fix is built; any compiler/parser-level fix (new builtin, new syntax) requires a fresh `--save`, not just a rebuild — a distinction that did not matter for fixes 1 or 3 below (pure runtime/VM behavior, no bytecode shape change).
3. **`LoadDefaultArgument` hard-failed resolving a missing callee's default argument, pre-empting `TRY*CALL*FORM`/`TRY*JUMP*FORM`'s documented "skip to `CATCH`" behavior for a genuinely absent function.** Argument evaluation (including default-argument lookups for omitted positional args) runs *before* the `Call`/`TryCall` instruction that would have skipped gracefully, so a missing-function default-arg lookup crashed hard first. Real corpus repro: `SYSTEM_STATUS_CALC.ERB`'s `TRYCCALLFORM SKILL_ADD_STATUS_%TEMP_SKILLS%, "HP補正", , L_CHARA, TEMP_SKILL, TRYSKILL_VAR` (note the omitted arg) names a function that legitimately doesn't exist for most skills. Switched the lookup from `get_func` to `get_func_opt`, pushing an inert placeholder when the callee is absent (`try_call` discards `args` outright in that case).

All three: regression-tested (`crates/erars-vm/tests/{split_sets_result,exists_function,try_call_missing_default_arg}.rs`, each independently confirmed to reproduce the real observed crash message when its fix is reverted), `cargo test --release -p erars-vm` 88/88 passed, `-p erars-ast -p erars-compiler -p erars-lexer` all green after the `BuiltinMethod` addition.

### 16.2 A fourth defect found and deliberately deferred: comma-separated bulk array-literal assignment is unimplemented

Past the third fix, character-role selection (any of the six classes — confirmed by reading `SET_MASTER_MAJORING.ERB`: every role's dedicated `SET_MASTER_MAJORING_*` sub-function returns into a shared `CALL SYNC_STATUS, MASTER` immediately after the `SELECTCASE`, so this is not one role's bug) crashes: `VM error occurred: Index convert error` at `SYSTEM_STATUS_CALC.ERB@1139`. Traced to `SYSTEM_STATUS_CALC.ERB:1134-1135`:
```

BTL_STAT_TABLE '= "공격", "명중", "방어", "회피", "마법위력", "마법효과"
```
followed by lookups like `HUMAN_BTL_STAT:FINDELEMENT(BTL_STAT_TABLE, "명중") = ...`. Confirmed via Emuera reference documentation (seesaawiki.jp, cross-checked against eragames.rip's `excom` wiki): `'=` (single-quote-equals) on a string array variable is a **bulk sequential-fill operator** — `STR:20 '= "a", "b", "c"` means `STR:20="a", STR:21="b", STR:22="c"`, filling consecutive elements starting at the target's base index, one value per comma-separated expression. This exists specifically because plain `=` with a comma-separated RHS on a string variable instead concatenates everything into *one* literal string (`STR = "a", "b"` assigns `"a, b"` to the single target index) — genuinely different, both officially documented, behaviors.

`crates/erars-compiler/src/parser.rs`'s `ComplexAssign::Str` arm currently does neither: `Some(ComplexAssign::Str) => { let rhs = expr(rhs); Stmt::Assign(var, None, rhs) }` — it parses the RHS as a single expression and performs one scalar assignment, identical to plain `=`, discarding the "fill consecutive array elements" semantics entirely. A search for how the analogous non-quoted case (`A:10 = 1, 2, 3`, documented to fill `A:10=1, A:11=2, A:12=3`) is implemented turned up nothing (`grep` for any comma-list/multi-value AST node or compilation path across `erars-ast`/`erars-compiler` returns no matches): **this comma-separated bulk-assign form is not implemented for either the plain-`=` or `'='` case, on either int or string arrays.** It is not a one-line fix; it needs a new parse path (splitting the RHS into a comma-separated expression list) and a new compilation strategy (N assignments to N consecutive indices from one source line, for both `Stmt::Assign` forms), applied consistently across both variable-type cases — a distinct, self-contained undertaking deserving its own session rather than a rushed addition appended to this one, especially since it is likely used throughout a corpus this large (a name→index lookup table like `BTL_STAT_TABLE` is a common idiom, not a one-off).

**Deliberately not fixed this session.** This is the natural stopping point for "as deep as reasonably reachable": three real, unrelated, narrowly-scoped defects were found and fixed in sequence; a fourth surfaced that is qualitatively larger (an unimplemented language feature, not a narrow lookup/behavior bug) and universal to every subsequent role-selection path, so no alternate menu choice reaches deeper. Continuing to chase further defects indefinitely would turn a bounded histogram-measurement task into an open-ended engine-hardening audit.
